# 📐 001 Стандарт ведення нотаток DNK OS: Міст між Людиною та Агентом

> [!abstract] **Призначення протоколу**
> Цей стандарт визначає єдиний формат записів у сховищі Obsidian, який однаково зручний для **людини-розробника** (візуальна ясність, контекст, навігація) та **AI-агента** (машинозчитувані метадані, точні шляхи до коду, відсутність галюцинацій).

---

## 🎯 1. Подвійна оптика (Dual-Reader Principle)

Кожна нотатка в цій бібліотеці створюється для двох читачів одночасно:

| Для Людини (Максим / Архітектор) 👤 | Для AI-Агента (Герич / Рій) 🤖 |
| :--- | :--- |
| **Зрозуміла українська мова** у поясненнях і висновках | **Англомовні назви** методів, коду, конфігів та шляхів |
| **Візуальні блоки Callout** (`> [!tip]`, `> [!warning]`) | **Суворий YAML Frontmatter** для фільтрації та пошуку |
| **Mermaid-схеми** для розуміння логіки за 5 секунд | **Машинозчитуваний хедер MRH** (`DNK-STD-0075`) |
| **Активні Wikilinks `[[...]]`** для кліку в один дотик | **Точні відносні шляхи до файлів репозиторію** (`apps/...`) |
| **Секція «Що далі / Action Items»** | **Чіткі інваріанти** (що категорично заборонено чіпати) |

---

## 🗂️ 2. Типи нотаток та їхні шаблони

Ми використовуємо 5 основних архетипів записів:

### 1. `ARCH` — Архітектурна специфікація / Модуль
- **Коли створювати**: Проектування нового сервісу, рефакторинг ядра, опис компонента системи.
- **Обов'язкові поля**: Що робить модуль, які файли в репозиторії йому належать, Mermaid-діаграма, API ендпоінти.
- **Приклад**: [[Gerych Prime - Unified Orchestrator & SOTA Adaptation Engine]].

### 2. `ADR` — Architecture Decision Record (Запис архітектурного рішення)
- **Коли створювати**: Коли ми робимо важливий вибір між альтернативами (наприклад, чому обрали FastAPI замість Node.js, або чому Remotion, а не FFmpeg CLI напряму).
- **Структура**:
  - `Контекст` (Яка виникла проблема?)
  - `Розглянуті варіанти` (Варіант A, B, C)
  - `Прийняте рішення` (Обрали X)
  - `Наслідки & Компроміси` (Що виграли, з чим доведеться рахуватися).

### 3. `SOTA` — Звіт асиміляції світових інновацій
- **Коли створювати**: Коли вивчили крутий GitHub-репозиторій чи наукову статтю.
- **Структура**:
  - `Джерело` (URL репозиторію, зірки, автор).
  - `Ліцензія` (Track 1 Permissive vs Track 2 Copyleft).
  - `Суть технології` (Які патерни підгледіли).
  - `Як це посилює DNK OS` (Якому агенту передаємо в роботу).

### 4. `PLAYBOOK` — Інструкція запуску / Гайд для розробника
- **Коли створювати**: Рецепти розгортання, траблшутинг, тестові сценарії.
- **Структура**: Точні консольні команди (bash), перевірочні логи, що робити, якщо впала помилка.

### 5. `AGENT` — Картка спеціалізованого агента
- **Коли створювати**: Для кожного з 14 агентів рою.
- **Структура**: Роль агента, його системний промпт, список дозволених інструментів, залежності в рої.

## 🗣️ 3. Що казати Геричу (Короткі тригерні фрази)

Щоб я створив нотатку потрібного формату без зайвих запитань, використовуйте прості команди:

---

## 🔄 3.1. Автоматичний збір знань (Post-Task Knowledge Harvest Invariant)

Після кожного успішного виконання значимої задачі, реалізації складного алгоритму чи важливого вибору технологій, Герич **автоматично ставить запитання**:

> 💡 **"Максиме, задачу виконано успішно. Чи бажаєте зафіксувати це рішення / алгоритм в Obsidian як [ADR / Специфікацію / Playbook] з описом, чому саме ми обрали такий підхід?"**

Вам достатньо відповісти:
- **«Так»** або **«Запиши»** — і Герич автоматично формує повний документ з обґрунтуванням, діаграмами та зв'язками, оновлює `000 DNK HUB Index` і фіксує контекст на майбутнє.
- **«Ні / Йдемо далі»** — продовжуємо роботу без створення зайвих записів для дрібних чи тривіальних задач.

1. **Для архітектури**:
   > *"Герич, зафіксуй архітектуру [назва] в Obsidian"*
   *(Я створю специфікацію з Mermaid-схемою, файловими зв'язками та лінками).*

2. **Для прийнятих рішень (ADR)**:
   > *"Збережи це рішення як ADR в Obsidian: чому ми обрали [X] замість [Y]"*
   *(Я запишу контекст, плюси/мінуси та фінальний вердикт).*

3. **Для досліджених бібліотек / GitHub**:
   > *"Герич, зроби SOTA-звіт в Obsidian по репозиторію [посилання або назва]"*
   *(Я перевірю ліцензію Track 1 / Track 2, витягну ключові патерни та розпишу інтеграцію).*

4. **Для інструкцій та запусків**:
   > *"Створи Playbook в Obsidian: як запускати та тестувати [модуль]"*
   *(Я збережу точні кроки та перевірочні команди).*

5. **Універсальна команда**:
   > *"Запиши це в мої нотатки Obsidian"*
   *(Я сам визначу тип нотатки, оформлю YAML, додам MRH, проставлю `[[wikilinks]]` та оновлю Головний Індекс).*

## 🔗 4. Золоте правило перелінковки (Obsidian Graph Invariant)

1. **Жодної «ізольованої» нотатки (Orphan Note)**:
   Кожна нова нотатка ОБОВ'ЯЗКОВО лінкується з [[000 DNK HUB Index]] та своїм материнським розділом.
2. **Семантичні зв'язки**:
   Якщо в тексті згадується агент, модуль або протокол — він береться у `[[подвійні дужки]]` (наприклад, `[[gerych_builder]]`, `[[TaskDNA Architecture]]`, `[[Master Quality Gate]]`).
3. **Зв'язок із реальним кодом**:
   У шапці або блоці метаданих завжди вказується відносний шлях до файлу в кодовій базі:
   `repo_source: "apps/api/routers/auth.py"` або `docs/architecture/...`.
