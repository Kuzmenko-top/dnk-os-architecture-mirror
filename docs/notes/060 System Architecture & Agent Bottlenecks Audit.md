# 🏛️ Архітектурний аудит: Реальні проблеми та вузькі місця системи DNK OS

## 📌 Вступне слово Головного Архітектора
Тести та перевірки нашого середовища показують 100% Green на рівні контракту та безпеки. Проте справжня зрілість інженерної системи вимірюється не відсутністю помилок у тестах, а тим, наскільки чесно ми усвідомлюємо архітектурні обмеження, "вузькі місця" (bottlenecks) та небезпеки деградації під час реального бойового навантаження.

Нижче наведено відвертий зріз поточних проблем та зон ризику системи.

---

## 🚨 1. Рівень ройових агентів (Swarm & Subagent Bottlenecks)

### Проблема 1.1: Синдром "Агента-Одинака" (Gerych Prime Bottleneck)
- **Суть**: Архітектурно задекларовано 14 спеціалізованих агентів (`gerych_builder`, `gerych_researcher`, `dnk_dev_fullstack`, `gerych_auditor` тощо). Проте на практиці більшість складних завдань виконує сам `gerych_prime` у монолітному сеансі.
- **Наслідок**: Замість справжнього паралельного виконання 3-4 процесів з ізольованими контекстами, Прайм змушений читати всі файли, писати всі правки й перевіряти тести самостійно. Це веде до швидкого вичерпання ліміту дій (25 дій на слайс) та втоми контексту.
- **Рішення**: Фізичний запуск субагентів через підпроцеси або ізольовані воркери з передачею чітких артефактів через файли `sessions/collab_thread/` чи IPC.

### Проблема 1.2: Асинхронний зворотний зв'язок між агентами (A2A Loop)
- **Суть**: Якщо воркер (наприклад, `dnk_shopify`) завершує роботу або падає з помилкою валідації, координатор часто дізнається про це постфактум або через polling файлів, а не через миттєву подію в черзі.

---

## 🧠 2. Контекст, Пам'ять та Втрата Фокусу (Context Diet & SCONES)

### Проблема 2.1: Context Compaction & Ступінь деталізації (LOD)
- **Суть**: У великих сесіях контекст неминуче стискається (Context Compaction). Після стиснення агент втрачає дрібні деталі попередніх кроків і починає "перевідкривати" стан (re-reading), якщо ключові факти не були зафіксовані в Obsidian або SCONES.
- **Рішення**: Жорстке дотримання протоколу MASE — обов'язкова фіксація слайсу в git та створення підсумкової нотатки в Obsidian до настання компакції.

### Проблема 2.2: SCONES L1/L2 vs L3
- **Суть**: Пам'ять SCONES зараз чудово працює на рівні JSON-файлів (`docs/scones/error_distillations.json` та `scones_memory.py`), але векторний пошук (L3 semantic search) спирається на прості ембедінги або текстове зіставлення без глибокого графового вилучення знань у режимі реального часу.

---

## 🗄️ 3. Сховище, Concurrency та Гігієна Робочого Простору

### Проблема 3.1: Засмічення робочого дерева (Git Tree Clutter)
- **Суть**: У репозиторії накопичилося 180+ змінених та 100+ невідстежуваних файлів (старі чорнетки в `docs/notes/tasks_and_ideas/`, сліди експериментів у `visual_shell/open_design`).
- **Небезпека**: Будь-який терміновий `git checkout` на іншу гілку блокується незбереженими локальними змінами. Потрібна планова сегрегація: архівувати застарілі чорнетки, зафіксувати стабільні фічі, решту додати в `.gitignore`.

### Проблема 3.2: Файлова база даних (`visual_shell_db.json`)
- **Суть**: Хоча ми захистили її за допомогою `fcntl.flock` в `atomic_store.py`, під час масштабування на десятки одночасних користувачів файловий JSON стане вузьким місцем (I/O contention).
- **Цільова архітектура**: Перехід на SQLite (з режимом WAL) або PostgreSQL для високонавантаженого продакшну.

---

## 🖥️ 4. Розрив між UI/Canvas та Живим Виконанням (Canvas ⇄ Engine Gap)

### Проблема 4.1: Пасивне відображення замість реактивного запуску
- **Суть**: На полотні React Flow (`apps/web`) користувач бачить граф TaskDNA, стан Sentinel та вузли. Проте перетягування зв'язку чи зміна статусу картки на UI поки що не запускає реактивний процес виконання агента на бекенді автоматично — це вимагає ручного виклику команди або API-тригера.
- **Ціль**: Перетворити полотно на **Live Cockpit**: зміна стану ноди на полотні ➔ виклик FastAPI WebSocket ➔ запуск відповідного Swarm Worker ➔ стрімінг логів прямо в ноду.

---

## 🔌 5. Продуктові модулі та Реальні Інтеграції

### Проблема 5.1: "Dry-Run" стан зовнішніх провайдерів
- **Shopify**: Двигун `dnk_shopify` вміє генерувати ідеальний Liquid AST та валідувати схеми, але взаємодія з реальним Shopify Admin API обмежена відсутністю живих продакшн-токенів у відкритому середовищі.
- **Video AI / Remotion**: Локальний рендеринг відео на CPU/GPU машини споживає суттєві ресурси; потрібен винесений worker-сервер для тривалих задач відеогенерації.

---

## 🗺️ Дорожня карта зміцнення (Actionable Roadmap)

1. **Етап 1: Гігієна Git & Робочого дерева**
   - Очистити робоче дерево: заархівувати тимчасові файли `tasks_and_ideas/`, створити чистий релізний зріз.
2. **Етап 2: Автономні сандбокси для Субагентів**
   - Перевести виклики `dnk_swarm_dispatch` на фізично ізольовані фонові процеси з обмеженим контекстом.
3. **Етап 3: Реактивний Canvas Cockpit**
   - Зв'язати події UI React Flow із чергою завдань FastAPI для запуску агентів прямо з полотна.
4. **Етап 4: SQLite WAL замість плоских JSON**
   - Мігрувати стан завдань та графів з `visual_shell_db.json` на SQLite WAL для безкомпромісної багатопотоковості.
